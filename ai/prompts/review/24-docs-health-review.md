# 24 文档体系周期性健康度复核

> Sync notice: This file is maintained by `ai-project-template` and may be overwritten when a derived project syncs template methodology.
> Do not edit it directly in derived projects; propose reusable changes in `_governance/_proposals/` and upstream them to the template repository.

**用途**：一轮工作（Sprint / Phase 收口，或连续多轮文档修改）收尾时，对文档体系做一次轻量健康度复核，识别「积累式演进」带来的臃肿、重复、结构退化和状态滞后等可读性副作用。

**目的**：补位现有「阶段触发 / 一次性」审计命令（docs-evaluation / docs-system-audit / docs-checklist）缺少的「周期性 / 收尾触发的可读性与信息密度检查」，让文档在多轮「分析-设计-实现-回流」后仍保持可读，读者能快速定位「当前在哪里、下一步做什么」。

**与 docs-system-audit 的区别**：`docs-system-audit`(16) 偏事后全链路追溯、断点 / 规范基线缺口、同步后回梳；本 Prompt 偏**可读性与信息密度**——内容重复、章节臃肿、结构退化、状态滞后，不重走追溯链与规范基线。两者互补，不替换。

**适用场景**：Sprint / Phase 收口、连续多轮文档修改后、或用户主动要求「梳理 / 瘦身 / 检查可读性」时。

**不适用场景**：

- 全链路追溯断点 / 规范基线缺口 / 阶段可行性 → `ai/prompts/review/16-docs-system-audit.md`。
- 阶段转换 `Go / Conditional Go / No Go` → `ai/prompts/review/19-docs-evaluation.md`。
- 编码前边界复查 → `ai/prompts/review/10-docs-checklist.md`。

**使用前准备**：本轮受影响的 `docs/00-09`、`docs/design/*`、`docs/research/*` 等文档；`ai/global-rules.md` §8（积累式演进）与 §8.4（整理例外）；无需完整规范基线对照。

**预期产出**：五类信号问题清单（定位 `文件:行` + 类型 + 严重度 + 建议处理方式）+ 按「可安全整理 / 需人工确认」分组 + 整理计划（按文档分组）+ 待人工确认项总览。**不改文件，先出报告。**

**使用后下一步**：确认后按 `ai/prompts/docs/04-edit-single-doc.md` 做最小整理变更；过时过程段落可移入 `docs/archive/`，遵守 `global-rules §8.4`。

```text
请基于 ai/global-rules.md §8（积累式演进）与 §8.4（整理例外）+ 本轮受影响的项目文档，做一次「文档体系周期性健康度复核」。

适用场景：一轮工作（Sprint / Phase 收口，或连续多轮文档修改）收尾时，对文档做轻量健康度复核，识别积累式演进的「臃肿 / 可读性」副作用。区别于 16（全链路追溯）/ 19（阶段评估）/ 10（编码前检查），本提示词聚焦可读性与信息密度，不重走追溯链与规范基线。

先界定复核范围：优先本轮改动文档 + 头部元信息 / 当前状态段 + 状态标记（待提交 / 待合并 / 待验收 / 已解决）密集区；避免全仓漫扫。范围大时先给 Batch 计划（一批一范围、报告先行）。

按以下五类信号逐段核查并输出：

1. 内容重复：同一事实 / 结论在多处重述，未引用权威源（横切事实应引用权威源而非各自声明，见 ai/document-lifecycle-rules.md §7）。
2. 章节臃肿：单章 / 单段异常超长（如把多阶段完成情况堆进单个表格单元格的超长头部元信息），信息密度失衡，读者难快速抓住「当前在哪里、下一步做什么」。
3. 结构退化：标题层级混乱、H2/H3 编号跳号或重复、过时过程性段落残留（见 ai/global-rules.md「文档编号规范」）。
4. 状态滞后：已完成事项仍标「待提交 / 待合并 / 待验收」等过程状态；已解决项与当前风险混排（见 ai/document-lifecycle-rules.md §7.1 状态词典；状态变化须传播）。
5. 表述语气：违反 `ai/global-rules.md` §10 的表述——无事实支撑的宣传口号、生活化比喻代替专业定义（行业通用术语如心跳 / 沙箱 / 灰度除外）、无依据的情绪化评价、空泛抽象词（赋能 / 闭环 / 全链路等）未说明对象或边界。属轻量语气检查，命中时给建议改写，不强制改写历史段落（§10 渐进适用）。

输出：

1. 健康度总览：复核范围、各信号命中数、整体可读性评估。
2. 五类信号问题清单。每个问题给出：类型、严重度（高 / 中 / 低）、文件:行、问题描述、建议处理方式。
3. 按「可安全整理」与「需人工确认」分组：
   - 可安全整理：纯过程性残留（如已完成但未推进的「待提交」标记、不再指向当前事实的临时描述、超长头部元信息可重构为「当前状态 + 历史指针」）。整理后仍能从当前文档追溯到全部历史事实。
   - 需人工确认：涉及历史事实 / 追溯锚点（REQ / 设计结论 / 验收记录 / 决策记录）/ 阶段结论 / 跨文档引用。按 ai/global-rules.md §8.4，历史事实须保留或进 archive，不得删除；不确定时一律标「需人工确认」。
4. 整理计划（按文档分组，标注可安全整理项的建议动作：推进状态 / 合并重述 / 重构头部 / 移入 docs/archive/）。
5. 待人工确认事项总览：使用结构化表格（ID / 来源文档或位置 / 待确认项 / AI 建议 / 建议依据 / 备选方案 / 取舍影响或阻塞关系）。

不改文件，先出报告；确认后按 ai/prompts/docs/04-edit-single-doc.md 做最小整理变更。整理动作必须遵守 ai/global-rules.md §8.4 整理例外：
- 允许：删除 / 合并已过时的过程性记录；将超长头部元信息重构为「当前状态 + 历史指针」；把过时过程段落移入 docs/archive/。
- 禁止：删除 / 改写历史事实与追溯锚点（REQ / 设计结论 / 验收记录 / 决策记录）——历史事实进 archive 或留一行指针。
- 判断准则：整理后仍能从当前文档追溯到全部历史事实；不确定时标「需人工确认」。

整理后聚焦自检：
1. git diff --check。
2. 对照「可安全整理」清单逐项确认过程性残留已推进 / 移除，旧状态标记无残留。
3. 确认未误删历史事实或追溯锚点；移入 archive 的段落仍可达（留指针）。
4. 确认整理未制造新的悬空引用（其他文档指向被移内容的位置）。
```
