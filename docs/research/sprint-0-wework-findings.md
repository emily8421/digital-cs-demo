# Sprint-0 企业微信外部群能力验证结论

> 核实日期：2026-06-21（v2 加固：在联网搜索基础上**直读企业微信官方文档原文**）。对应 `docs/08-dev-plan.md` Sprint-0。
> 目的：核实愿景 ⚠️——「企业微信客户群（含外部微信联系人）机器人/自动回复接收与应答外部用户消息」是否可行，决定 REQ-15 是否升 P1。
> **本文件是验证产出物，不是 00-09 设计文档**；结论回写影响 REQ-15 / 03 §3 / 00 前提风险。
> **核查方法**：(1) 联网搜索聚合公开资料；(2) 直读官方原文 4 篇——智能机器人·接收消息(path/100719)、主动回复(path/101138)、消息推送/原群机器人(path/99110)、微信客服概述(path/94638)，标注「原文」/「二手」。**未做**：实拨 API、官方工单求证。

## 1. 待验证问题（来自愿景文首 ⚠️）

1. 客户群（含外部微信联系人）能否**接收**外部用户消息？
2. 能否**应答/自动回复**？
3. 接口权限、调用频率限制？
4. 是否需要企业认证？

## 2. 结论速览

- **愿景原前提（客户群内 AI 被动监听并自动回复外部用户消息）：❌ 官方文档无任何机制支持。**
  - 消息推送（原「群机器人」Webhook）：**只发不收**〔原文 path/99110：「向这个地址发起HTTP POST请求…给该群组发送消息」〕、**20条/分钟**〔原文〕；「外部群不可加」=二手（原文未述群类型），但收发单向是原文铁证。
  - 智能机器人：能收（**@机器人/单聊**触发，加密回调）+ 能回（`response_url`，1 小时有效、每次一条，原文 path/101138）；**但接收消息回调里的 `from.userid` 是「企业主体下的userid」**〔原文 path/100719〕——交互对象是企业内部成员，**原文全文未出现「外部联系人/客户群」**。→ 由外部微信用户在客户群 @ 触发的可能性**原文层面不成立**；仅理论上有「tmp_external_userid 转换 / 自建应用对接」桥接，需官方确认。
  - 会话内容存档：能拿外部会话内容，但属「数据与智能专区」、**需客户同意**〔原文侧栏〕、合规**禁止用于自动回复**〔协议/二手〕——不可作自动回复通道。
- **最可行且合规的替代通道：微信客服（1:1 AI 客服）**——API 完整（消息与事件全回调给企业 + 收发/分配会话 API，原文 path/94638）、**自带「知识库问答」机器人**〔导航原文〕、接入微信内外各场景；**但它是 1:1 咨询入口，不是「客户群群内」形态**，会改变愿景的 UX 前提。
- **对 Demo 的影响：无。** Demo 一律走内置模拟器（REQ-1），核心价值不受阻塞。
- **对真实通道（REQ-15）的影响：原「客户群群内自动回复」路径不成立；需改方案**（见 §4）。

## 3. 逐通道证据（标注「原文」/「二手」）

| 通道 | 接收消息 | 发送/回复 | 客户群(外部群) | 判定 |
|---|---|---|---|---|
| 消息推送（原群机器人）| ❌ 只写〔原文〕| ✅ POST，20条/分钟〔原文〕| ❌「仅内部群」〔二手，原文未述群类型〕| **不可用**（单向+频控；外部群不可加=二手） |
| 智能机器人（@触发）| ✅ 加密回调〔原文 path/100719〕| ✅ `response_url`，1h/条〔原文 path/101138〕| ⚠️ 回调 `from.userid`=企业成员〔原文〕；外部联系人/客户群**原文未出现** | **群内外部用户触发：原文层面不成立**（理论桥接待官方确认） |
| 会话内容存档 | ✅ 拉取式〔专区〕| ❌ 非回复通道 | ✅ 含外部〔需客户同意〕| **不可用**（合规红线〔协议/二手〕） |
| 微信客服 | ✅ 消息与事件全回调〔原文 path/94638〕| ✅ 收发+会话分配 API〔原文〕+自带知识库问答〔导航原文〕| n/a（1:1 咨询，非群）〔原文〕| **可用但改形态**（最可行） |
| 企业群发 | n/a | ✅ 推送 | ✅ 频控严〔二手 约1条/天/群〕| 仅适合日报/通知 |

**原文关键摘录**：
- 〔path/100719 智能机器人·接收消息〕「当用户与智能机器人发生交互…交互事件将加密回调给机器人接收消息url」；`from.userid`「如果智能机器人创建者为企业超级管理员，则为明文userid，否则为**企业主体下的加密userid**」；触发场景仅「用户群里@智能机器人或单聊」「用户单聊中…」——**全文无「外部联系人/客户群」**。
- 〔path/101138 主动回复〕「回调中会返回一个 response_url…使用response_url主动调用接口回复消息」「每个 response_url 用户可以调用接口一次，有效期为 1 个小时」。
- 〔path/99110 消息推送/原群机器人〕「向这个地址发起HTTP POST请求，即可实现给该群组发送消息」「每个消息推送发送的消息不能超过20条/分钟」——**只述发送，无接收、无群类型说明**。
- 〔path/94638 微信客服概述〕「用户可以发起咨询，企业可以进行回复」「该账号的微信客户与企业接待人员的所有消息与事件都回调给企业…企业…调用API来收发消息、分配会话」；接入场景＝视频号/搜一搜/网页/公众号/小程序/微信支付凭证（微信内）、App/微信外网页（微信外）；侧栏含「机器人管理→知识库问答管理」。

## 4. 决策建议

> 本节为核实时的即时建议；**该决策的持续追踪与最终拍板记录在 `docs/decisions/open-decisions.md` DEC-1**。

1. **Demo（P1）**：按既定走**内置模拟器**（REQ-1），演示核心价值，**不阻塞**。Sprint-1 起即可推进。
2. **真实通道（REQ-15）改方案（待人工拍板）**：
   - **(A) 改走「微信客服」1:1 AI 客服〔原文证实可行，推荐〕**：API 完整、**自带知识库问答**、合规风险低、可快速落地；代价是 UX 从「客户群群内」变为「客户经客服入口 1:1 咨询」——**需与愿景方确认是否接受形态变化**。
   - **(B) 争取「智能机器人入外部群」〔原文层面不支持，存疑〕**：原文 `from.userid` 为企业成员、全文无外部联系人——**仅当官方确认存在外部用户桥接时才成立**；即便成立也可能仅 @触发、非被动监听全量消息。**可能性低，不建议作为主路径**。
3. **混合方案〔推荐〕**：AI 自动应答走微信客服(1:1)；企业微信**消息推送/内部群机器人**仅用于向员工推送「转交/提醒/日报」（合规可用）——即客户侧（微信客服）与员工侧（内部群）分离，员工侧仍保「消息通道、无需登录系统」。
4. **需向企业微信官方确认的点**：
   - 外部/客户群能否添加「智能机器人」并接收 @消息？（决定方案 B 是否成立）
   - 微信客服的频控、会话时效、能否承载 AI 全自动应答？
   - 所选方案是否强制企业认证、具体权限项。
