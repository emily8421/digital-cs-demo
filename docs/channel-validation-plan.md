# 通道验证路线（Channel Validation Plan）

> 定位：**非商用对比研究**。回答「用真实数据跑通需要什么、合规要付出什么代价」。
> 不直接面向真实客户投产；产出是一张 I/O 载体对照矩阵 + 可行性结论。
> 命名遵循 global-rules §5（语义化，不占 00-09 编号）。

## 0. 合规认知（前提）

**合规风险集中在两个 I/O 边界**：输入（获取客户群消息）与输出（自动回复客户）。中间架构（超时检测 / AI 判定 / 通知负责人 / 存档）**合规中性**。

→ 因此策略是：中间架构用模拟器先验证；真实数据的 I/O 边界，用**两种载体并列对比**，量化「合规代价」。架构本身（通道适配层）平台无关，只换适配器。

关联：`docs/design-channel-adapter.md`（三适配器）、`docs/sprint-0-wework-findings.md`（Sprint-0 结论）、`docs/open-decisions.md` DEC-7。

## 1. 三步路线

| 步骤 | 通道（适配层实现） | 目的 | 状态 / 对应 |
|---|---|---|---|
| **一** | `simulator`（模拟器，模拟 I/O） | 验证**整体架构**端到端跑通 | ＝ Sprint-1 / MVP（先行、不阻塞） |
| **二** | `wxautox-real`（真实微信号，wxautox4 式） | 用**实际数据**验证；与三对比 | MVP 跑通后，并行 Spike |
| **三** | `official-compliant`（会话存档采集 + 飞书通知 + 微信客服回复） | 用**实际数据**验证；与二对比 | MVP 跑通后，并行 Spike |

二与三**并列、可对比、非商用**——把「要不要上个人微信」从商用 go/no-go，降维成同一架构、同一批真实数据、两种 I/O 载体的对比研究。

## 2. 二 vs 三 对比矩阵（验证的真正产出）

| 维度 | 二·真实微信号（wxautox4） | 三·合规途径（会话存档+飞书+微信客服） |
|---|---|---|
| 采集覆盖 | 任意群（含外部微信客户群）✅ | 仅企业微信客户群，需客户同意 |
| 采集延迟 | ~5 分钟轮询 | 拉取式，有小延迟 |
| 自动回复 | 群内可发（但封号风险） | 群内自动回复**受限**（存档禁自动回复 → 改微信客服 1:1） |
| 合规 | ❌ 违微信协议 | ✅ 官方 |
| 稳定性 | 脆弱（锁版本、单点） | 稳 |
| 成本/门槛 | 低 + 养号成本 | 企业认证 + 会话存档付费 |
| 能力边界 | 全群内双向，但不可商用 | 合规、可商用，丢掉「群内全自动回复」 |

**产出结论**：「要合规，丢掉『群内全自动回复』，换来不封号、稳定、可商用」——是有信息量的取舍，而非空谈「能不能做」。

## 3. 风险 containment（非商用，风险可控但必须管）

针对 **Step 二（灰路径）**：
- **专用测试号**：不用真实业务号/客户号。
- **隔离测试群**：不拿真实客户群喂灰路径（客户不知情＝个保法问题）。
- **采集（read）为主**：自动回复（write）最谨慎，或仅触发不真发。
- **数据隔离**：抓取的真实聊天数据 demo 后清理，不长期留。
- **严格封在适配层**：实现只落在 `backend/channels/`，抽掉不影响中间架构与合规路径。
