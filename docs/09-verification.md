## 1. 测试策略

- **单元测试**：覆盖可独立判定的纯逻辑——留资抽取/脱敏、路由规则解析、小结聚合、检索阈值判定。`tests/`，pytest（待确认）。
- **集成测试**：经模拟器通道投递消息，验证端到端编排（检索作答/缺口转人/留资/小结），不依赖企业微信。
- **验收测试**：对照 `docs/03-prd.md` §3 Demo 脚本逐条走查；以 02-srs 的可验证口径为判据。
- **数据夹具**：愿景种子知识（IP65/67、5050/2835、户外型号、起订量/交期/付款）、模拟群与角色（小雯/阿杰/老黄/陈总）。
- **环境**：Docker 本地（PG + 应用 + 模拟器）；企业微信相关用例在 Sprint-0 验证通过后补真实环境冒烟。
- **红线**：任何分支不得在无知识依据下生成产品参数/退换结论/进度（对应愿景「不乱猜」）。

## 3. 用例详情（代表性）

### TC-REQ-1：模拟器入站归一化

- 覆盖 REQ：REQ-1
- 前置条件：后端启动，SQLite 单测或本机 PG 可用。
- 测试步骤：向 `POST /api/v1/messages/simulate` 投递文本消息，再读取会话详情。
- 期望结果：消息字段齐全，进入统一编排管线；切换通道不改业务逻辑。
- 自动化位置：后端消息 / 编排相关测试；端到端见 `demo-script.md`。

### TC-REQ-6：知识缺口转人工

- 覆盖 REQ：REQ-6
- 前置条件：知识库未覆盖测试问题，路由规则和员工种子已加载。
- 测试步骤：投递冷门问题，观察客户侧留资提示、缺口记录和员工侧通知。
- 期望结果：不编造答案；生成 open gap、handoff 与 notification。
- 自动化位置：编排 / 知识缺口相关测试；演示路径见 `demo-script.md` §4。

### TC-REQ-13：知识确认回写

- 覆盖 REQ：REQ-13
- 前置条件：存在 open gap。
- 测试步骤：拍板人补答生成 pending，再确认 pending 知识。
- 期望结果：知识状态变为 confirmed，并回填 gap；后续相似问题可命中。
- 自动化位置：P2 知识回写测试；页面演示见 `/ui`。

### TC-REQ-14：SLA 扫描

- 覆盖 REQ：REQ-14
- 前置条件：存在超过阈值未答的入站消息。
- 测试步骤：调用 `POST /api/v1/sla/scan`。
- 期望结果：生成时效提醒，不误标愿景真实通道能力。
- 自动化位置：SLA 相关测试；Demo 手动触发，生产形态由外部 cron 调用。
