## 背景

中小灯具（灯带/驱动电源等）经销/生产企业，普遍以**即时通讯群（IM 客户群）**作为主要售前售后触点。
真实痛点（取自愿景叙事，可回锚）：

- **夜间/忙时消息积压**：凌晨到早上的消息无人看，次日逐条翻拣，常发现客户已转投竞品（锚点：早上八点四十·灯带采购群·老周凌晨两点提问）。
- **峰值时段并发**：上午十点群内多客户同时提问，客服顾此失彼、漏回（锚点：上午十点·工程客户群定制询盘 + 采购基础问题并发）。
- **复杂定制询盘拆解难**：客户把长度/节数/线色/防水等多要求堆在一句话里，回复方漏确认一项即导致生产返工（锚点：上午十点·500 节灯带定制需求）。
- **售后话术踩雷**：质保边界类问题若机械回答「超过 X 月不退」，客户情绪升级、口碑受损（锚点：下午两点·林老板驱动电源售后）。
- **业务判断分散**：产品参数等业务知识归属在老板/固定对接人，员工各自记忆、口径不一（锚点：尾声·防雷参数由陈总拍板）。

**前提性技术风险（已核实）**：本场景原依赖「企业微信客户群（含外部微信联系人）支持机器人/自动回复接收与应答外部用户消息」。**Sprint-0 核实结论：该路径在企业微信标准能力下不成立**（客户群不能加群机器人、会话存档禁止用于自动回复）；真实通道需改方案（候选：微信客服 / 智能机器人入外部群），详见 `docs/research/sprint-0-wework-findings.md`。MVP 不受影响（走内置模拟器，见 REQ-1）。

## 目标用户

| 角色 | 在场景中的职责 | 本系统的关系 |
|---|---|---|
| 群内客户（经销商/工程采购/终端） | 提问产品参数、定制询盘、订单进度、售后 | 系统服务的最终用户，侧体验＝普通群消息 |
| 一线客服（如 小雯） | 售前接待、报价跟进 | 接收系统「该跟一下」的提醒，接管留资/询盘 |
| 售后/技术（如 阿杰） | 售后核实、上门处理 | 接收带上下文的售后转交，避免从零追问激化情绪 |
| 跟单（如 老黄） | 订单/生产进度 | 接收订单进度查询转交（售中） |
| 经营者/固定业务决策人（如 陈总） | 业务知识拍板、当日重点关注 | 接收定时小结；对新增业务知识做确认 |
| 新员工（如 小桐） | 监看群、转交不能答的 | 不需学新系统，像「转头问老板」一样工作 |

> 涉及业务判断的内容（如产品参数答案）由经营者/固定对接人确认；技术提供方仅做整理录入，**业务知识归属与决定权留在客户一方**。

## 典型场景

1. **售前知识问答**：客户问灯带防水等级/型号选型，系统自动从知识库作答（锚点：早上·老周 IP67/选型）。
2. **标准品采购引导**：客户问起订量/交期/付款方式，系统秒回带具体数字（锚点：上午十点·三基础问题）。
3. **定制询盘引导**：复杂定制需求被拆成多项逐条确认（锚点：500 节×1 米、焊接引线、黑红线、防水）。
4. **询盘留资 + 人工接管**：客户满意留联系方式，系统抽取出并提醒指定客服跟进（锚点：老周 138\*\*\*\*6677）。
5. **订单进度转人工（售中）**：客户问工序进度，系统未打通生产记录则如实转跟单并附订单信息（锚点：下午四点·PO-20260603-07）。
6. **售后规则引导 + 转人工**：质保边界类售后，系统先安抚并转交技术、附购买时间/视频提示，不直接给退换结论（锚点：林老板驱动电源）。
7. **知识缺口发现 + 确认回写**：答不上的问题让客户留资、转交拍板人；拍板人答复后系统征询「是否作为以后标准答案」并记录（锚点：防雷参数）。
8. **定时小结**：给经营者每日定点摘要「今天要关注什么、该跟的已分给谁」（锚点：中午 12 点 / 傍晚小结）。

**边界场景（决定系统能力边界，单列于 01/02）**：转人工后 AI 暂停（避免人机说法不一）、AI 身份披露（被问是否机器人）、语音/非文字消息处理（如实告知不能识别并提醒人工）。
