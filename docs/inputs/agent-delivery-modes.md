# 智能体交付形态输入材料

> **定位**：原始输入包 / 待评审材料。本文用于记录“数字客服智能体可能需要支持的交付形态与交互入口”，**不直接定义开发范围**，不等同于已批准需求。
>
> **来源**：2026-06-29 产品化讨论；用户补充的 6 类智能体交付形态；现有文档中的 Demo/H5、公众号、企业微信、员工辅助工具、平台直连、邮件等线索。
>
> **使用方式**：后续先用 `ai/prompts/docs/01-review-inputs.md` 做输入评审，再决定哪些内容回写到 `docs/vision/product-vision.md`、`docs/00-scenario.md`、`docs/01-user-requirements.md`、`docs/02-srs.md`、`docs/03-prd.md` 及设计文档。
>
> **影响范围候选**：若确认纳入路线图，可能影响交付物形态、客户入口、员工入口、通道适配、前端形态、API、安全、部署、验收脚本。
>
> **当前状态**：待人工评审；不得直接据此实现功能。

## 1. 背景

当前数字客服已完成 P1/P2 Demo：H5/网页 + 后端编排 + 本地知识库 + 演示控制台，可演示“客户消息有人接、答得上的自动答、答不上的转人、经营者收到小结”。

进入产品化 D 时，需要先回答“智能体交付给客户时，客户拿到的是什么、怎么用它”。现有愿景更多描述业务场景和客服能力，未系统覆盖不同交付形态。本文先把可能的交付入口作为上游输入沉淀，供后续评审和路线图拆分。

## 3. 逐形态说明

### DM-1 网页 / H5 链接

- **入口**：H5 链接、二维码、PC 控制台、知识确认页。
- **输入层**：用户在网页输入问题；当前 Demo 通过模拟器接口进入后端编排。
- **输出层**：页面展示 AI 回复、缺口转人提示、留资结果、多轮询盘追问等。
- **适用场景**：演示、试用、员工辅助、门店现场、临时分享。
- **优点**：零安装、开发成本最低、最快验证交互闭环。
- **缺点**：客户感知上更像工具页面，不像独立正式产品；真实客户流量入口弱。
- **阶段建议**：Demo 已覆盖；MVP 可保留为试用 / 管理 / 员工辅助入口。
- **可能影响**：前端体验、登录/权限、手机适配、分享链接、访问控制。

### DM-2 微信公众号

- **入口**：客户关注公众号后，在公众号内发送咨询。
- **输入层**：公众号 Webhook 将客户消息推送到系统。
- **输出层**：系统通过公众号消息接口回复客户。
- **适用场景**：客户主动咨询、标准 FAQ、售前询盘、活动引流。
- **优点**：微信生态内，客户熟悉；官方 API，合规；比 H5 更像正式入口。
- **缺点**：客户需要关注公众号，和现有“微信群/直接加人”习惯有迁移成本。
- **前置条件**：客户是否愿意关注公众号；公众号主体、认证、菜单、消息接口权限。
- **阶段建议**：产品化 D 的正式入口候选；需先做客户入口验证。
- **可能影响**：新增通道适配器、Webhook 签名、会话身份映射、菜单/引导话术、验收用例。

### DM-3 企业微信机器人 / 工作群机器人

- **入口**：企业微信内部工作群中机器人消息、@机器人、员工通知群。
- **输入层**：员工在内部群触发机器人，或系统向内部群推送待办/日报。
- **输出层**：机器人向员工群发送转交、SLA、日报、知识确认提醒；必要时员工再回复客户。
- **适用场景**：员工协作、经营者小结、转交提醒、内部知识问答。
- **已知边界**：企业微信外部客户群内自动回复已被 Sprint-0 证伪；不能把“外部客户群自动客服”作为主路径。
- **优点**：员工无需登录后台，符合“消息通道内协作”；内部通知合规性更高。
- **缺点**：客户侧不直接触达；若涉及外部群，需要另行验证官方能力。
- **阶段建议**：作为员工侧协作入口纳入产品化候选；外部客户群机器人仅保留为官方确认项。
- **可能影响**：员工身份映射、通知模板、群机器人配置、权限、审计、失败重试。

### DM-4 桌面端应用 / 安装包

- **入口**：客户下载安装 Windows / macOS 应用，本地打开使用。
- **输入层**：用户在桌面应用输入问题、上传资料或接入本地文件/设备。
- **输出层**：应用展示回复、生成内容或控制本地工具。
- **适用场景**：强“软件产品感”的工具型智能体，如 AI 调光工具、设计辅助工具、本地资料处理工具。
- **优点**：客户感觉“买到一个软件”；可做本地文件、设备、离线能力。
- **缺点**：开发/测试/发布/升级/兼容成本高；当前数字客服资源和场景不优先。
- **阶段建议**：暂不纳入数字客服 MVP；可作为另一条工具产品线或远期产品形态。
- **可能影响**：桌面技术栈、自动更新、本地数据安全、安装包签名、跨平台测试、离线模型资源。

### DM-5 嵌入客户自有系统 / API

- **入口**：客户现有网站、小程序、ERP、CRM 或工单系统调用数字客服 API。
- **输入层**：宿主系统通过 API 传入消息、客户、订单、工单等上下文。
- **输出层**：智能体返回建议回复、转交结果、知识命中、结构化摘要等，由宿主系统展示。
- **适用场景**：已有技术团队或现成系统的客户；需要把智能体能力嵌入既有流程。
- **优点**：能力可复用，适合平台化和 B2B 集成。
- **缺点**：古镇小厂通常没有可集成系统；项目实施依赖客户 IT 能力。
- **阶段建议**：远期开放能力；当前只保留内部 API 清晰性，不作为首批交付入口。
- **可能影响**：开放 API 设计、鉴权、租户隔离、限流、版本管理、SDK、集成文档。

### DM-6 小程序

- **入口**：客户在微信内搜索、扫码或从聊天中打开小程序。
- **输入层**：小程序前端发送客户消息和身份信息到后端。
- **输出层**：小程序展示 AI 回复、留资、进度、知识确认或人工接管状态。
- **适用场景**：希望比公众号更有独立产品感，同时仍在微信生态内触达客户。
- **优点**：产品感强于公众号；可承载更丰富页面和业务流程。
- **缺点**：开发周期、审核、运营配置高于公众号；客户是否愿意打开小程序需验证。
- **阶段建议**：产品化候选；应与公众号做成本/客户习惯/能力边界对比后再决定。
- **可能影响**：前端技术栈、登录授权、微信小程序审核、消息订阅、页面路由、隐私合规。

## 5. 后续评审问题

1. 客户侧第一入口应该优先选：H5、公众号、微信客服、小程序，还是员工代用？
2. 古镇小厂客户是否愿意从微信群迁移到公众号 / 小程序 / 微信客服入口？
3. 员工侧是否必须在“消息通道内”工作，还是可以接受一个 Web 控制台？
4. 哪些形态只是演示/试用入口，哪些形态才是可收费交付物？
5. 桌面端应用是否属于数字客服主线，还是另一个智能体工具产品线？
6. API 嵌入是否需要现在预留开放能力，还是只保持内部接口清晰？
7. 如果多个形态都可能需要，是否应先抽象“通道适配层 + 前端入口层”，避免后续重复实现？
